## 发布检查流程

1. 使用固定 Node `26.8.1` / npm `11.19.0` 执行 `npm ci`，检查锁文件无意外变化。
2. 运行 `npm run build`、`npm run test:portable` 和记忆回归；在 macOS arm64 额外运行 `npm run test:mac`。命令见 [参与维护](../CONTRIBUTING.md)。
3. 保留项目及第三方许可，执行 `npm pack --ignore-scripts`，用 `tools/release/verify-package.py` 核对安装包成员。
4. 在独立 DSH_HOME / Profile 验证安装、冷启动、项目与 Thread、续聊、迁移、停用及卸载。脚本模型测试不能替代真实模型质量验证。
5. 用 `tools/release/scan-security.py --history --package <tgz>` 检查源码、历史和安装包。逐项审查匹配，不直接忽略未分类结果。
6. 为安装包和发布附件生成 SHA-256 校验和，核对版本、标签、许可、迁移说明及发布说明。
7. 确认对应提交的 GitHub Actions 通过，再发布 Prerelease，并明确不设为 Latest。

GitHub Actions 负责构建、可移植离线测试、项目记忆回归和 Memory 界面测试，不自动发布。安装、桌面操作、实际文档读取、真实服务和真实模型行为需要分别验证。安装测试使用独立 Profile；真实服务写入和模型调用要先确认数据、费用与目标范围。

## CI 临时目录

测试入口优先使用 `DSH_TEST_ROOT`，其次使用 GitHub runner 的 `RUNNER_TEMP`，否则使用系统临时目录。Linux 测试目录应位于 checkout 和 `/tmp` 之外。13 项依赖 macOS 租约机制的测试在 Linux 跳过，其他 Git 安全测试继续执行。

## 标签与发布附件

产品变更生成新版本并重新验证。保留旧标签、Release 和安装包，不能通过覆盖旧文件让旧版本指向不同实现。

在线文档和 Release 说明可以补充限制、修正措辞；这些修订不自动重打安装包。核对旧安装包时，以对应标签为准。若更新单独下载的发布说明，也要更新包含其摘要的 `SHA256SUMS.txt`。
